# Chapter 9 - Methods

Functions allow code to be reused.

As programs grow, however, many functions naturally become associated with a particular type.

For example, a `Vec2` type might have functions for calculating its length or adding another vector.

A `File` type might have functions for reading or writing data.

In Coda, these functions are called **methods**.

Unlike some languages, methods are simply functions associated with a type.

They introduce no new runtime behaviour.

---

## Defining a Method

A method is declared by qualifying its name with a type.

```coda
struct Vec2 {
    float32 x;
    float32 y;
}

fn float32 Vec2.length(Vec2 this) {
    return math::sqrt(this.x * this.x + this.y * this.y);
}
```

This declares the `length` method for the `Vec2` type.

The first parameter is the value the method operates on.

By convention, this parameter is named `this`.

---

## Calling a Method

Methods are called using the `.` operator.

```coda
Vec2 position = {
    .x = 3,
    .y = 4,
};

float32 length = position.length();
```

This is equivalent to writing:

```coda
float32 length = Vec2.length(position);
```

The two forms are identical.

The method syntax exists purely for readability.

---

## Mutable Methods

Methods may modify their receiver.

```coda
fn none Vec2.normalise(mut Vec2 *this) {
    // ...
}
```

Because `this` is a pointer to a mutable value, the method can update the original structure.

The method is called in exactly the same way.

```coda
position.normalise();
```

---

## Methods Are Not Members

It is important to understand that methods are **not stored inside a type**.

Structures contain only data.

Methods are ordinary functions.

This means that adding a method does not change the memory layout of a structure.

It also means that methods can be reasoned about exactly like any other function.

---

## No Implicit Function Calls

Calling a method is always explicit.

Simply accessing a field never invokes user-defined code.

```coda
player.score
```

reads a field.

```coda
player.score()
```

calls a method.

The two operations are completely distinct.

This is one of Coda's core design principles.

---

## Methods and Namespaces

Methods belong to the namespace of their type.

Two unrelated types may define methods with the same name.

```coda
fn none Window.close(...)

fn none File.close(...)
```

There is no ambiguity because the type determines which method is being called.

---

## Choosing Between Functions and Methods

Both forms are useful.

Consider the following function.

```coda
fn float32 distance(Vec2 left, Vec2 right)
```

This operation treats both parameters equally.

Writing it as a free function clearly communicates that neither value is more important than the other.

By contrast:

```coda
position.normalise();
```

clearly expresses that the operation conceptually belongs to `position`.

As a general guideline:

* use methods when an operation naturally belongs to one type,
* use free functions when several values participate equally.

Neither form is more powerful than the other.

---

## Putting It Together

```coda
module geometry;

struct Vec2 {
    float32 x;
    float32 y;
}

fn none Vec2.translate(mut Vec2 *this, float32 dx, float32 dy) {
    this.x += dx;
    this.y += dy;
}

@entry
fn none main() {
    mut Vec2 position = {
        .x = 10,
        .y = 20,
    };

    position.translate(5, -3);
}
```

Although the method syntax looks different, the compiler treats it exactly like an ordinary function call.

## Experimenting

Try the following:

* Add a method that resets a vector to the origin.
* Create a method that returns the larger of two fields.
* Rewrite a method as a free function.
* Compare which version feels more natural.

Remember that methods are simply another way of organising functions.
